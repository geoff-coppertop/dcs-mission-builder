# dcs-mission-builder

Code-built DCS World missions and campaigns. Every mission here is generated by a Python script with
[pydcs](https://github.com/pydcs/dcs), runs its own logic in the DCS scripting engine (plain Lua, no MIST or MOOSE),
and comes with a briefing written in Markdown that becomes both the PDF and the briefing text inside the `.miz`.

## Campaigns

| Campaign | Aircraft | Missions | |
|---|---|---|---|
| [Operation Narrow Gate](campaigns/narrow_gate/README.md) | F/A-18C, 1–2 players | 8 files, branching on how each mission goes | [`dist/narrow_gate`](dist/narrow_gate) |

To fly a campaign, copy its `dist/<campaign>/*.miz` files into `Saved Games/DCS/Missions` and open the first one.
Each mission's summary tells you which file to fly next, and its `_Briefing.pdf` sits alongside it.

## Building

```
pip install -r requirements.txt
playwright install chromium          # once, for the PDF step
python build.py                      # every campaign
python build.py narrow_gate          # one campaign
python build.py narrow_gate --only briefings     # re-render briefings after editing Markdown
python build.py narrow_gate --no-tests
```

A build runs these stages in order:

1. **missions**: the campaign's `build_*.py` scripts write the `.miz` files to `dist/<campaign>/`.
2. **maps**: theater and target maps and timelines, drawn from the built missions into `build/<campaign>/`.
3. **briefings**: each Markdown briefing is filled in from its mission, rendered to `dist/<campaign>/*_Briefing.pdf`,
   and its in-game sections are written into the `.miz`.
4. **checks**: every ground unit and ground waypoint is on land.
5. **tests**: each mission's Lua runs against a mocked DCS scripting API, under Lua 5.1 (as DCS uses) and Lua 5.5.

`dist/` is committed so the missions can be downloaded without building; `build/` is not.

## Layout

```
build.py                    the build entry point
missionbuilder/             shared Python
  builder.py                mission scaffolding: carrier, player flight, tanker, AWACS, CAP, drone, scripts
  briefing.py, briefing.css Markdown briefings -> PDF and in-game text
  mapkit.py                 map drawing and .miz parsing
  red_arms.py               explicit Red fighter loadouts (pydcs can't load DCS defaults without an install)
  geom.py, landcheck.py     mission geometry export; ground units on land
lua/                        shared mission scripts
  common.lua                messages, geometry, lasers, recovery tracking, event dispatch
  cap.lua                   controller-run CAP: MAGIC commits on criteria, resets, alert-5 relief
testing/mockdcs.py          a stand-in for the DCS scripting API
campaigns/<name>/
  README.md                 the campaign: story, missions, how they connect
  campaign.py               the campaign's build stages
  build_*.py                one script per mission (or family of variants)
  lua/                      the campaign's mission scripts
  briefings/*.md            briefing templates
  context.py                the numbers each briefing needs, read from the built mission
  maps_*.py                 the campaign's maps
  tests/                    scripted scenario tests
dist/<name>/                built .miz files and briefing PDFs
```

## Writing briefings

Briefings are Markdown with [Jinja2](https://jinja.palletsprojects.com/) placeholders, so the prose never
disagrees with the mission: `{{ tot }}`, `{{ restart }}`, `{% if hard %}…{% endif %}`. The values come from the
campaign's `context.py`, which reads them from the built `.miz`. An unknown placeholder fails the build.

Three HTML comments decide what goes into the mission file as well as the PDF:

```
<!-- ingame -->   …   <!-- /ingame -->      the mission description in the DCS briefing screen
<!-- task -->     …   <!-- /task -->        the "Blue task" text: times, route, comms, menus
<!-- pdf-only --> …   <!-- /pdf-only -->    left out of the in-game text even inside those blocks
```

Everything is in the PDF. In the in-game text, headings become capitals, tables become one line per row, and
images are dropped. A few HTML helpers are available for the PDF: `<div class="pagebreak"></div>`,
`<div class="keep" markdown="1">…</div>` to keep a heading with its table, `<div class="glance" markdown="1">`
for the at-a-glance box, and `{: .medium }` or `{: .short }` after an image to cap its height.

After a build, `build/<campaign>/<mission>.md` is the filled-in Markdown and `<mission>.context.json` the values
behind it, which is the quickest way to check a briefing.

## Adding a campaign

Create `campaigns/<name>/` with a `campaign.py` that defines the five stage functions (`missions`, `maps`,
`briefings`, `checks`, `tests`), each taking the build's campaign object (`c.run(script, *args)`, `c.out`, `c.work`,
`c.dir`). `campaigns/narrow_gate/campaign.py` is a complete example.

All scenarios are fictional and for DCS World training.
